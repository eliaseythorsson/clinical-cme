# The engine handles the store: recognise, rebase, write folders

Until 5.x the store was prose (`store.md` §4): the assistant matched the files a read tool saved to their store paths, copied the publish set into a folder by hand, checked the folder ledger's `gen` (in prose only; neither the tests nor the simulation did) and, after a refused publish, re-ran the job's commands itself. Each of these is procedure, and procedure belongs in `cme.py` (ADR 0001). Decided in the architecture review of 2026-11-26 (issue #57):

- **Recognise by content.** `open` (and `start --store`) finds every store document in the store copy by its place, its bare name or its content (ledger, page file, old index, prepared round, page, session, review and testing documents). Where two files hold the same document, the one written last counts. The log's folders (`data/sessions/`, …) are not walked, so opening costs the same whatever the history.
- **One seam, two adapters** (`publish_job`). The page adapter emits the publish set (`files`, `publish.json`): only the assistant can call the artifact tools. The folder adapter (`cme.py publish`) writes it into the folder itself, in write order, each file written beside and moved into place, after checking that the folder's ledger is byte for byte the one the job read (or its own last write). A folder store's ledger is snapshotted at `open` (`ledger_read.json`), so another device writing to the folder changes nothing of the job until it publishes. Tests and the simulation publish through the folder adapter.
- **Rebase on conflict.** Every command that writes is a step of the job, noted in `work.json` (a file named in its options kept as given), and puts its **token** (the job's random id and the step's number) into the ledger it publishes (`applied_steps`, the latest 64; a step that writes no ledger publishes the ledger with only its token added, `gen` unchanged). When a publish is refused (`open --reread` on a fresh read for the page; `publish` itself for a folder), the fresh ledger alone says which steps the store holds: every step up to the last whose token it lists, since a publish carries all before it. Nobody has to say that a publish landed. Only the later steps run again, through the same commands, so the result is what those commands give ("apply the recorded round to the fresh ledger", issue #74). The job's own log documents are put back as the store holds them (as the job first read them, then as the last publish that landed carried them; snapshotted per step), never from a store copy a half-finished folder write may have changed, so a page rebase reads only the four top-level files. A round already in the store is never recorded twice; a round another device recorded from the same ledger is kept, this job's round renumbered and applied after it, in save order. A round finalised without its reflection by such a round still gets its reflection when it arrives. A round prepared ahead on the ledger as it was is dropped (written live next time). A `save` or `close` run again as it stands is the same step, applied again in place.
- **What the learner hears.** A clean rebase says nothing. One line when something of theirs changed: their round was renumbered after another device's; the round mix changed on another device while a round was played here (the round keeps the mix it was played with); a setting changed here that another device had changed meanwhile (this change replaces it). Never a question during a close.

Between two copies of a document the file at its store path wins, then its bare name, then the higher `gen`, never the newer file (a sync tool's conflicted copy is never the ledger). The folder check is check-then-write, not atomic: a device writing between the check and the last file is not detected; the ledger is written last, so the worst case is the later writer's files replacing the earlier one's.

Consequences: `store.md` is reduced to what to read and what to publish, plus recovery. The assistant no longer re-runs commands after a conflict. Not handled: two devices racing a third time during one rebase (the publish stops, nothing more is written, recovery as before); more than 64 writing steps of other jobs between a job's read and its publish: its tokens would have left the list, so its steps would run again (a round then recorded twice, an addendum added twice).
